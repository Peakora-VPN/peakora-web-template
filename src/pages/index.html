The connection lifecycle

From request to response

Follow the stages that turn a name into a delivered page.

Start with a name

Name resolution connects a domain to an address. A cached answer can let the browser move straight to the next stage.

Establish the connection

The browser negotiates a transport and, for a secure connection, completes a handshake. An existing connection may be reused.

Send the request

The request crosses the network and the server prepares a response. The wait for its first byte includes both parts of that journey.

Bring the response back

The response arrives in the browser, ready to be interpreted. The page can then request its styles, fonts and other resources.

Edge delivery

Where a request meets the network.

The edge is a boundary between a client and the systems serving it. Name resolution, transport negotiation and response delivery all contribute to the experience on the other side.

Connection setup
Account for the cost of establishing a new connection and the benefit of reusing one.
Protocol negotiation
Let the client and server agree on a supported way to exchange requests and responses.
Response delivery
Understand the difference between waiting for a response and transferring its content.

Transit & routing

The path matters as much as the destination.

A connection depends on the networks between its endpoints. Physical distance is only part of the picture: routing decisions, congestion and transport behavior also affect delivery.

Path awareness
Consider the complete route rather than treating the destination as the only variable.
Changing conditions
Expect a route's behavior to vary with the network, the client and the time of the request.
End-to-end context
Read latency and transfer measurements together to understand where time is spent.

Operating principles

Consistency is an operational choice.

The details around a connection matter just as much as the connection itself. These principles guide how we think about infrastructure.

Understand the path before drawing conclusions

A slow page can have several causes: resolution, connection setup, waiting for a response or transfer. Looking at those stages separately makes the next question more useful than treating every delay as the same problem.

Make changes deliberate and reviewable

A repeatable baseline makes differences easier to understand. Changes should have a clear purpose, a way to check their effect and a path back when the result is unexpected.

Keep the context that makes a report actionable

A timestamp in UTC, the affected address and a description of what happened are useful starting points. Whether an issue repeats, affects one client or appears across several networks also helps narrow the investigation.

Common questions

A little more context.

What does edge infrastructure mean?

The edge is the client-facing boundary of a network or service. It is where connections are handled before requests move through the rest of a system. Delivery, transport and operational decisions meet at that boundary.

Why can two visits feel different?

The browser may reuse a connection or a cached name lookup. Network conditions can change too. The result is a different balance of setup, waiting and transfer time, even when the requested page is the same.
