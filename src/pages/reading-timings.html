One response, two clocks.

A browser can say when a response started to arrive and when it finished. Everything interesting about delivery hides inside those two readings, and treating them as one number throws the interesting part away.

Navigation Timing

The browser keeps its own timeline.

Every navigation is stamped with high-resolution marks: when the lookup ran, when the connection opened, when the request was sent, when the response began and when it ended.

The value of a single mark matters less than the distance between two marks. Each interval is a phase of the request path, and a phase appears only when the browser both measured it and chose to expose it. Reading the timeline means reading those intervals, never the marks alone.

Marks, not causes

A timeline records when something happened, not why. It can show that the waiting interval grew; explaining the growth takes context the numbers alone do not carry.

Relative time

The stamps count from the start of the navigation, not from the wall clock. They describe this load, on this connection, in this browser, and nothing beyond it.

Exposure limits

Browsers can withhold or round marks for privacy and precision reasons. An absent stamp is a property of the measurement, not a failure of the page.

Waiting and transferring

TTFB and transfer measure different worlds.

Time to first byte runs from the request going out to the response starting to arrive. Transfer runs from that first byte to the last. The first interval is a wait; the second is a delivery.

  1. 01 / The request travels

    The outbound trip is part of the wait

    Time to first byte starts before the server has anything to answer with. The request's own journey across the network is inside the interval from the beginning.

  2. 02 / The response is prepared

    Queueing and generation join the wait

    The same interval also holds everything that happens before the first byte can leave: waiting for a handler, preparing the response. A long wait is a sum of parts, and the timeline by itself does not say which part grew.

  3. 03 / The response crosses back

    Transfer begins where the wait ends

    From the first byte to the last, the transfer interval describes the delivery of this document's bytes. It can be short while the wait was long, or the reverse; the two move independently and deserve separate readings.

Reading with context

A number becomes useful next to its neighbors.

A duration means little alone. These comparisons keep single readings from being over-read.

The document is not the page

The measured response is the main document. Styles, fonts and images are requested separately and are not inside its transfer time, so the number never describes a fully rendered page.

One load is a sample

A single visit inherits whatever caching, connection reuse and path it happened to get. Only repeated readings separated in time begin to describe behavior rather than luck.

Waiting and transferring move apart

A change in server preparation shifts the wait without touching transfer, and a congested path can do the opposite. Moving one number without the other is a clue about where to look.

The reading stays with you

Navigation timing is computed in the browser from its own observations. This site reads it locally for display and sends nothing anywhere; there is nothing to correlate or retain.

Questions

Why do the numbers change between reloads?

Caching, connection reuse and the network path can all differ between visits. Each reading describes its own load, so variation between reloads is expected rather than suspicious.

Is the transfer duration a measure of my bandwidth?

No. It covers one document's response, which is a small and timing-sensitive workload. It says nothing about the sustained capacity of your connection.

Why is a phase missing from the scale?

Phases reported as zero, or not reported at all, are omitted rather than invented. A reused connection legitimately has no setup phases to show.
