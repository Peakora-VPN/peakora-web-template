Peakora Network / Articles / Connection reuse

Setup is a toll, not a destination.

Every fresh connection pays for its own opening: a transport handshake, then a secure handshake on top. None of it moves a request a single byte. The cheapest setup is the one that is not repeated.

Secure transport

A handshake is a negotiation with stakes.

Before data flows, the two ends of a connection have to agree on who is on the other side and how the conversation will be protected while it lasts.

Authentication

The server presents a certificate that binds its name to a public key. The client checks that chain of trust before it relies on anything else about the connection.

Key agreement

The two sides derive shared secrets without ever sending them across the network. From that point the channel has keys that only its ends hold.

Parameters

The handshake also fixes the protocol version and the algorithms in force for this connection. Two connections to the same host can settle on different answers.

The security negotiated here protects everything the connection later carries. It applies to the channel, whatever requests and responses travel over it.

A fresh connection

Round trips are the currency of setup.

A handshake is measured in exchanges, and every exchange costs at least one trip across the network. Setup time is dominated by latency long before bandwidth matters.

  1. 01 / Open the transport

    TCP settles its own opening exchange

    Before anything application-shaped moves, the client and the server trade three short messages to open the channel and synchronize their starting state.

  2. 02 / Secure the channel

    The secure handshake rides on top

    Authentication and key agreement add exchanges of their own. Newer protocol revisions fold most of the work into fewer round trips than their predecessors, but on a fresh connection the work never reaches zero.

  3. 03 / Speak

    The first request leaves only now

    Every setup exchange stands between the visitor and the first byte of the response. That is why connection opening is felt most on the very first load and least on a busy, returning one.

Connection reuse

The next request should not pay again.

Once a connection exists, keeping it open and sending more work through it removes the entire setup phase from every later request.

Persistent connections

Modern HTTP is built to leave a connection open after a response. The next request to the same host travels on the existing channel instead of opening a new one.

Session resumption

When a new connection is unavoidable, a server can hand the client a ticket that lets a later session skip part of the handshake and reach protected data sooner.

One connection, many requests

Multiplexed protocols carry many requests and responses over a single connection at the same time, so parallel page assets no longer mean parallel handshakes.

Newer transports

The newest HTTP revision folds its secure layer into the transport itself. Setup still costs exchanges, but the timing boundaries a browser reports no longer split along the old lines.

Reuse is why repeated visits can feel instant even when the first one did not: the expensive part was already paid. For where setup sits in the wider request path, see the network guide.

What you can observe

Reuse looks like missing phases.

On a reused connection, the timing marks for connection setup collapse onto each other. The browser reports the request and the response, and nothing in between.

A readout with no transport or secure handshake is not hiding work; it is reporting that the work did not happen. This site draws the phases your browser reports and omits the ones it does not, so a warm visit can show nothing but the request itself and its answer.

Questions

Why does the first load feel slower than the following ones?

The first load pays for name resolution, transport setup and the secure handshake. Later loads can reuse each of those results, leaving only the request and its response.

Is a reused connection less protected than a fresh one?

No. Reuse continues the protection negotiated when the connection opened. Keeping a channel open does not weaken its encryption or its authentication.

Why is there no secure-handshake phase in my timings?

Either the connection was reused, so no new handshake ran, or the browser chose not to expose the mark. Here phases that cannot be measured are omitted rather than guessed.

How do I report a transport problem?

Write to {{CONTACT}} with the hostname, timestamps in UTC and what you observed. Repeated occurrences are more useful than a single snapshot.
