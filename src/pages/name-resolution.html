Peakora Network / Articles / Name resolution

A name is a question.

A hostname is easy for people to remember and useless for a machine to dial. Before any connection can start, the name has to be translated into an address, and every step of that translation is designed to happen as rarely as possible.

The lookup path

From typed name to usable address.

Resolution is a chain of questions. Each link answers a little more of the original query until one of them can answer it completely.

  1. 01 / Ask locally

    The browser and the operating system check first

    A browser keeps recent answers in its own cache, and the operating system keeps a separate one that every application shares. If either layer holds a fresh answer, resolution is over before the network is involved at all.

  2. 02 / Ask the configured resolver

    An unanswered name goes to a recursive resolver

    The system forwards the query to the resolver provided by the network. From this point the client simply waits while the resolver does the walking on its behalf.

  3. 03 / Walk the hierarchy

    Root, top-level zone, authoritative server

    The resolver asks a root server where the top-level zone is handled, asks that registry where the domain's authoritative servers live, and asks one of those servers for the record. Each hop is its own exchange, and a cold answer can take several round trips to collect.

  4. 04 / Cache the answer

    The record comes back with a lifetime attached

    The answer arrives carrying a time to live set by the zone's operator. Every cache along the way may keep the record for that long and answer from memory instead of asking again.

Caching

The whole system is built to skip work.

DNS is cached at every layer, because repeating a full lookup for every connection would add delay without adding any new information.

Browser cache

The browser keeps its own list of recent answers and checks it before bothering the rest of the system. It is the closest cache and usually the first to be hit.

Operating system cache

Every application on the device shares this layer. One program's lookup can spare the next program the entire question, whatever the program is.

Resolver cache

A resolver serves many clients at once, so its cache is shared the widest. A frequently requested name is usually answered from memory long before the hierarchy needs to be asked.

Time to live

Each record carries its own expiration, chosen by the zone's operator. A short lifetime spreads corrections quickly; a long one trades slower corrections for fewer lookups.

Caches can also hold a negative answer. When a name does not resolve, many resolvers remember the failure briefly, so one mistyped name does not trigger a fresh walk on every try.

What you can observe

The lookup is visible only when it happens.

Navigation Timing reports the DNS phase as the interval between the start and the end of the lookup. A warm cache makes those two marks coincide, and the phase disappears instead of appearing as a measurable step.

That absence is the cache working, not a gap in the page. Here the readout draws only the phases your browser reports, so a repeat visit can legitimately show no resolution at all. The network guide places this stage among the rest of the request path.

Questions

Why did the DNS phase vanish on my second visit?

The answer was already cached by your browser, your operating system or the resolver. Cached lookups skip the network entirely, so there is no interval left to measure.

Does a cached answer mean the address never changes?

No. It means the answer is still inside its declared lifetime. Once that lifetime expires, the next lookup asks the hierarchy again and changes spread as caches refresh.

Who decides how long an answer is kept?

The operator of the authoritative zone sets the record's time to live, and well-behaved caches honor it. A cache may shorten the lifetime, but extending it would serve stale answers.

How do I report a resolution problem?

Write to {{CONTACT}} with the hostname, the approximate time in UTC and what you observed. That context is enough for a useful first check.
